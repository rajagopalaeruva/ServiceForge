## 1. Coverage rule

Before the plan goes to review: every `Must` functional requirement appears in at least one task; every accepted ADR appears in at least one task; every ADR claim that is not yet verified has a verification task; every task has an owner role, inputs, an output and a done check; no task depends on a later one. `scripts/check-plan.ps1 -Feature 2` checks this. A done check names only what that task can prove at its position in the order.

## 2. Tasks

Task IDs are `T-n` (`T-v1` for a verification task), stable once the plan is approved, never reused. A withdrawn task is marked *Withdrawn*, not deleted. Statuses: Todo, Doing, Built (Developer), Verified (Tester).

Tests come in two kinds. The **Developer's unit tests** (T-1 to T-4) are written with the code, prove the service and request-type behaviour of that task, and are tagged `F2U_AC_n` and `F2U_EC_n`; `check-traceability.ps1` does not count them. The **independent HTTP tests** (T-8 and T-8b) are written from the spec, the ADRs and sections 2.1 and 2.2 by a writer who never sees the implementation, prove the behaviour at the HTTP boundary, and carry the tags `F2_AC_n`, `F2_EC_n` and `ADRnnn_`; they live in classes separate from the Developer's tests. Acceptance criteria AC-18 to AC-20 (user interface) are verified by a recorded walkthrough performed by the human (spec v2.0), and AC-16 by the full-suite run (T-9); both are waived in the traceability check. Independent `ADRnnn_` cases are owned as follows: ADR-001 by T-8b; ADR-002 by T-8 (AC-5, AC-12, AC-14, EC-3, EC-5) and T-8b (AC-6, EC-11); ADR-003 by T-8 (AC-15, AC-21, AC-22); ADR-004 and ADR-005 by T-8. The Developer's own ADR-related tests (T-2, T-3) are tagged `F2U_ADRnnn_` and are not independent.

### 2.1 Endpoint contract (proposed by the planner; approved together with the plan)

The spec fixes behaviour, not paths. The planner fixes the HTTP contract here so the independent tests (T-8 and T-8b) and the build (T-5, T-6) work to the same contract. Class, package and DTO names are the Developer's; paths, methods and JSON field names are not. A change to this contract after approval is a plan change.

| Operation | Method and path | Request body | Success | Errors (all with an `ApiError` body, in the order of FR-12) |
|---|---|---|---|---|
| Stock view | `GET /api/parts` | none | 200, a list of `{ "id", "name", "available" }` | none |
| Reserve | `POST /api/jobs/{jobId}/reservations` | `{ "lines": [ { "partId": <integer>, "quantity": <whole number> } ] }` | 201, `{ "jobId", "reserved": [ { "partId", "quantity" } ] }`, one entry per part, quantities summed for this request | 400 invalid request or non-numeric `jobId`; 404 unknown job, then unknown part; 409 job not `SCHEDULED`, then insufficient stock |
| A job's reservations | `GET /api/jobs/{jobId}/reservations` | none | 200, a list of `{ "partId", "quantity" }`, all successful reservations summed per part; an empty list if none | 400 non-numeric `jobId`; 404 unknown job |

Every rejection changes no stock and no reservation. Feature 1 endpoints and the `Job` JSON do not change.

**Message contract** (every message is the `message` field of an `ApiError`): a 400 follows `pipeline/rules/api-error-contract.md` (the field name, or `Malformed request body`); a 404 names the unknown id (job or part); the 409 for a job that is not `SCHEDULED` names the job id and its current status; the 409 for insufficient stock names the first short part by ascending id with the requested and the available quantity (ADR-002, `_index.md` Q-A). Tests assert that these values appear in the message, not the exact sentence. For a 400, tests assert a non-empty `message`, that an unreadable body gives exactly `Malformed request body` (`api-error-contract.md`), and that a failed field check names the field. Lists are in ascending id order: `GET /api/parts` by part id, and `reserved` and `GET /api/jobs/{jobId}/reservations` by part id.

Order and parallel work: T-v1, T-2, T-8 and T-8b have no dependencies and can start together once the spec re-approval and the plan approval are done. T-1 follows T-2. T-3 follows T-v1 and T-2. T-4 follows T-1, T-2 and T-3. T-5 follows T-4, T-8 and T-8b. T-6 follows T-5, then T-7. T-9 follows T-5 and T-8b. T-10 follows T-7 and T-9. T-11 is last.

### 2.2 Test conditions for the independent HTTP tests

These rules are part of the contract; the independent writer receives them with 2.1.

- **State.** Any test that asserts exact stock or a job's exact reservations (including AC-1 to AC-8, AC-17, AC-21 and EC-4 to EC-8) start each test method from a fresh application context, so in-memory state is the seed data.
- **Restart (AC-22).** After a reservation is made in one application context, a second, separate application context is started and `GET /api/parts` must equal the A-1 catalogue and a job's reservations must be empty.
- **Seed data.** The A-1 catalogue: parts 1 to 5 with 12, 25, 6, 3 and 0 available. On a fresh context Feature 1 seeds three `SCHEDULED` jobs with ids 1, 2 and 3.
- **Other jobs.** Tests create `COMPLETED` and `CANCELLED` jobs, and change a job's status for EC-7, with the existing Feature 1 `MockDataStore.save`, `MockDataStore.nextJobId` and `Job`. No Feature 2 class is used.
- **Concurrency (AC-17, EC-8).** A fixed number of threads is released together; the tests assert totals (granted, rejected, final stock), not timing.

### 2.3 Walkthrough and live-check procedure (T-10)

- **Who runs the application.** `frontend/src/environments/environment.ts` points the UI at `http://localhost:8080/api`, so the walkthrough needs the backend on port 8080. After T-7 is built, the human starts the backend (`mvn -q spring-boot:run` from `backend/`, port 8080) and the frontend (`npm start` from `frontend/`, port 4200) and stops them afterwards.
- **Checklist and record.** The Tester supplies a checklist for the stock view, AC-18, AC-19, AC-20 and NFR-5 (labels, keyboard use, messages announced), including counting the interactions for M-5, and records the human's pass or fail per item in the spec's evidence.
- **Live check.** The live-check runner uses its own free port and never 8080.
- **Non-`SCHEDULED` jobs (RV-31).** Decided by the human on 2026-11-17: the walkthrough covers AC-18 for `SCHEDULED` jobs only (the seed has no other status and no endpoint changes status); the "not offered" half is shown by the T-11 code review of the status condition in the Angular code. The independent HTTP tests show only that the API rejects a reservation for such a job with 409 (AC-13); they cannot show that the UI hides the action. The narrowing is recorded as a deviation in the spec's evidence and signed off by the human at T-10.

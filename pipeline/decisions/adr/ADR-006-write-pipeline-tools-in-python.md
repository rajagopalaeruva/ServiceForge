# ADR-006: Write the pipeline check tools in Python with JSON output

Related: ADR-000, `pipeline/orchestration.md`, `scripts/pipeline.py`, `scripts/pipeline_tools/`, `scripts/tests/`

## Context and Problem Statement

The pipeline checks (status, entry gates, plan coverage, traceability, push scan, ADR guard) are PowerShell scripts in `scripts/*.ps1`. They parse markdown tables and front matter with regular expressions and print text only, so another program has to scrape that text. There are no automated tests for them. PowerShell does not report a misspelled variable until the line runs. One script (`check-plan.ps1`) also carries a dependency filter with a corrupted character that never had any effect (see Consequences).

## Decision Drivers

* D1: Results are machine-readable, so other programs and agents can consume them without scraping text.
* D2: The checks are unit-testable without touching the real pipeline files.
* D3: The tools stay read-only.
* D4: No third-party packages. A new language runtime is acceptable only if it is added to the documented prerequisites (`AGENTS.md`).
* D5: Behaviour stays the same as the PowerShell scripts during the change, and every difference is listed.
* D6: The tools run on any OS that has the runtime and git. Only Windows with Python 3.13 has been tested (Python 3.9 or newer is expected to work). Use `py` on Windows and `python3` elsewhere. The current `.ps1` files need PowerShell.

## Considered Options

* Option A: Keep PowerShell and add a `-Json` switch to each script.
* Option B: Python 3 package using only the standard library, one command per check, `--json` on each.
* Option C: Node.js, plain JavaScript (`.mjs`, `node:test`), same layout as B.
* Option D: TypeScript on Node.

## Decision Outcome

Chosen option: "Option B: Python, standard library only". Rajagopal Aeruva chose Python on 2026-11-21 (recorded by the assistant on his instruction), after the design review (DR-1, DR-12) showed that Python is not yet a documented prerequisite. Python 3 is therefore added to the prerequisites now (`AGENTS.md`, "How to run it").

Layout: `scripts/pipeline.py` is the single entry point (`status`, `gate`, `plan`, `traceability`, `push`, `guard-adr`). The logic is in `scripts/pipeline_tools/`. Each command except `guard-adr` returns a dictionary and prints it as text by default or as JSON with `--json`. `guard-adr` is a hook helper that prints one JSON line or nothing. Text output is UTF-8 on every console; characters the console cannot show are replaced, never raised. Tests use `unittest` and are in `scripts/tests/`.

Exit codes (the same as the script each command replaces):

| Command | 0 | 1 | 2 |
|---|---|---|---|
| `status` | status printed | not used | no spec file, or unrecognised spec status |
| `gate` | gate passes | gate fails (including no spec) | not used |
| `plan` | coverage OK | problems found (including no spec or no plan) | not used |
| `traceability` | nothing required is missing (optional items only warn), or legacy spec skipped | required test missing, an optional one with `--strict`, or no spec | not used |
| `push` | no BLOCK findings | a BLOCK finding, or a WARN finding with `--strict` | range cannot be resolved, or `git` is not found on PATH |
| `guard-adr` | always (never fails; it decodes stdin as UTF-8 and ignores errors) | not used | not used |

Command-line usage errors (unknown role, `--feature all`, missing argument) exit 2 in Python (`argparse`). The `.ps1` scripts exit 1 for the same mistakes.

### Consequences

* Good: stable JSON for every check; 74 tests that build their own temporary repos; the gate logic is shared by `status` and `gate` instead of being a subprocess call.
* Bad: two implementations exist until the PowerShell scripts are retired, so a rule change must be made twice in that period. Python 3 becomes a prerequisite. On this machine the `python` alias only opens the Microsoft Store; `py` works.
* Neutral: `feature: all` means this ADR never blocks any feature gate, like ADR-000. `--feature` is a number, so the tools cannot be pointed at "all".
* The dropped filter in `check-plan.ps1` (`$t.Depends -notmatch '^(<corrupted>|-|none)?$'`) changed nothing, because the next step keeps only tokens that start with `T-`. The Python port keeps that step (`_deps`) and has no filter.

Known differences from the PowerShell scripts (all other output and exit codes are the same on the parity fixtures):

1. `gate` prints the closing `GATE FAILED` line when the spec is missing; `check-gates.ps1` stops after the `FAIL:` line.
2. `push` prints one line per finding instead of a `Format-Table` table. The findings, masking and BLOCK/WARN counts are the same. The order of findings that differ only in the file name can differ: PowerShell sorts text by culture rules, Python by code point.
3. Command-line usage errors exit 2 (see above).
4. Status and priority words, task ids, dependencies and `--waive` ids are compared without regard to case, as in PowerShell. Known status words are printed in their canonical spelling. Unknown task statuses are grouped without regard to case and named by their first spelling, like `Group-Object`; the order of those groups can differ for non-ASCII or punctuated names (culture rules against code point). Ids, priorities and dependency names are printed as written in the file (for example `ac-1`, `AC-2 (should)`, `t-1 -> T-2 -> t-1`). `--role` is accepted without regard to case and printed as typed. A missing status prints as an empty value, not `None`.
5. Text is split only on CR, LF and CRLF, as in .NET. Files are decoded like `ReadAllText`: a UTF-8 BOM is ignored, and a UTF-16 or UTF-32 BOM selects that encoding.
6. Text output is written as UTF-8 with replacement for characters that cannot be encoded. PowerShell prints `?` for characters outside the console code page.
7. `.pushscan-allow` is read as UTF-8 (or by BOM). `check-push.ps1` reads it with the `Get-Content` default code page, so it does not match an entry for a non-ASCII file name; Python applies that entry as written. This is looser than the reference only for entries the reference fails to apply, and it is what the author of the entry meant. It is not replicated.
8. `guard-adr` prints the same JSON object. The bytes are identical for ordinary ADR names (checked on ADR-000: 125 bytes, same SHA-256). They can differ for names with special characters: Windows PowerShell 5.1 escapes `'`, `&` and `<` (as `\u0027` and similar) and Python escapes non-ASCII characters. The parity test compares the parsed objects. For a non-ASCII ADR name the `.ps1` depends on the console code page: the Reviewer saw it print nothing under the default code page (it misreads the hook JSON), while in this session, with a UTF-8 console, it printed the same decision as Python. Python always decodes stdin as UTF-8.
9. `push` scans text after a lone CR in an added line, which `check-push.ps1` skips (it splits git's output at the CR). Python reads git's output as bytes and splits on LF only, so it is stricter than the reference on purpose: the scan guards a public remote. Line numbers follow git's own hunk counts.
10. `push` checks the names of sensitive files whose path git would quote: non-ASCII characters (for example `dé/k.pem`) and a tab, newline, backslash or double quote. The `.ps1` misses them, because git quotes such paths in `diff-tree` output (`"d\303\251/k.pem"`) and the file-name rules do not match the quoted form. Python reads the names with `diff-tree -z`, which never quotes. Stricter than the reference on purpose. This covers the file-name rules only (see item 13).
11. `push` decodes git's output as UTF-8 with replacement; the `.ps1` uses the console code page. A key glued directly to a non-ASCII letter such as `é` is found only by the `.ps1`, and a key glued to a stray invalid byte is found only by Python. A key after a space or punctuation is found by both. Not replicated.
12. The `push` text report shows control characters (including C1, U+2028 and U+2029), format characters such as U+202E, U+200B and U+FEFF, and a backslash as escapes (`\n`, `\r`, `\t`, `\\`, `\xNN`, `\uNNNN`, `\UNNNNNNNN`) in file names, details, the range and error text. A crafted name cannot split a finding over several lines, imitate a report line, reorder the displayed text or send terminal escape sequences. The escaped form is unambiguous (a backslash is doubled). Letters in any script stay readable. `--json` keeps the exact names. The `.ps1` prints names raw (and, for names git quotes, never sees them, see item 10).
13. A content finding in a file whose name git quotes (tab, newline, backslash or double quote) has an empty file name in both Python and the `.ps1`, because the diff header `+++ "b/..."` is not parsed. I ran both with a tab, a backslash and a double quote in the name: 3 findings with an empty name, in both. Non-ASCII names are not affected: the content scan runs with `core.quotepath=off` and shows the real name. The finding is still reported and still blocks. `.pushscan-allow` cannot match it, so the error is on the strict side. Not changed, to stay equal to the reference.

### Confirmation

* `py -m unittest discover -s scripts/tests` passes (74 tests, under two minutes).
* `scripts/tests/test_cli_and_parity.py` runs the original `.ps1` and the Python command on the same fixtures and compares text and exit code: `status` on 14 fixtures (every phase, no spec, an unrecognised status), `gate` for 4 roles on 7 fixtures, `plan` on a good and a bad plan, `traceability` with and without `--strict` and `--waive`, and `guard-adr` on 4 payloads. It also covers upper and lower case words and ids, a UTF-16 spec, and non-ASCII file names, and it checks the JSON keys per command and the exit codes. It does not compare `push` text with `.ps1` (the layout differs on purpose); `push` was compared once by hand on a seeded repo and on this repo, and has its own tests, including a secret after a form feed or U+2028.
* The parity tests are skipped where PowerShell is not available, so they stop being a check once the `.ps1` files are retired.

## Pros and Cons of the Options

### Option A: Keep PowerShell, add `-Json`

* Good, because it has no behaviour change (D5), no new prerequisite (D4), and no rewrite.
* Bad, because regex parsing and weak typing stay, and it needs PowerShell (D6). It can meet D1 and D2, but there are no tests for it today, and Pester would be the test tool (not evaluated).

### Option B: Python, standard library only

* Good, because it meets D1 to D4 and D6 with built-in `json`, `re`, `unittest` and `argparse`, and it is already built and tested.
* Bad, because Python 3 becomes a new prerequisite (D4, now documented) and two implementations exist during the transition (D5 needs the parity tests).

### Option C: Node.js, plain JavaScript

* Good, because Node is already needed for the frontend and the repo already runs a Node tool from a hook (`.kiro/hooks/memory-sync.json`), so it adds no prerequisite (D4); `npm` is already a documented prerequisite in `AGENTS.md`. `JSON` and `node:test` are built in.
* Bad, because it means rewriting the same checks again (about 850 lines of Python are already done and tested), and it has no static typing. It meets all drivers; it was not chosen because of that rewrite cost and the owner's decision.

### Option D: TypeScript on Node

* Good, because types could be shared with the Angular frontend.
* Bad, because it needs a compile step or a runner such as `tsx`, plus tooling configuration for code that is not frontend code.

# Feature 2 — Parts Availability and Reservation

| Field | Value |
|---|---|
| **Status** | Candidate-built / in progress |
| **One-line intent** | Check available stock and reserve requested parts for an existing scheduled job. |
| **Depends on** | Feature 1's **Buffered Interval Detection** decision in `pipeline/decisions/feature-1-decisions.md`: booked jobs occupy `[start, end + 45 minutes)`, and exactly 45 minutes between jobs is allowed. |
| **In scope** | Provide a stock-and-reservation flow using seeded, in-memory inventory, accessed from the existing technician calendar. The user can see all parts and their currently available quantities, select a job with status `SCHEDULED`, and reserve one or more parts using positive whole-number quantities. A job may receive multiple reservations over time while stock remains. If the same part appears more than once in a request, sum its quantities before checking availability and recording the reservation. Each successful request is associated with the selected job and immediately reduces available stock; inventory and reservations reset when the application restarts. Each request is all-or-nothing: if any requested part's total quantity is unavailable, reject the entire request without changing stock or existing reservations. Invalid quantities are rejected without mutation. A reservation does not create, move, or alter the job's booked slot. |
| **Out of scope** | Creating, editing, or rescheduling jobs; changing Feature 1's booking or 45-minute travel-buffer rules; releasing, editing, or cancelling a reservation, including release when a job is completed or cancelled; editing/replenishing stock, low-stock alerts, purchasing, supplier workflows, authentication, and persistent database storage. |
| **Definition of Done** | 1. The stock view lists seeded parts with an identifier, name, and current available whole-number quantity; a subsequent stock view reflects each successful reservation's stock reduction. 2. The existing technician calendar offers reservation only for jobs with status `SCHEDULED`; a successful reservation response and UI confirmation identify the job and reserved quantities. 3. A request containing multiple parts succeeds only if each part's aggregate requested quantity is available; it records all requested quantities against the selected job and decreases each corresponding available quantity by that aggregate. 4. A later reservation for the same job succeeds when stock remains, and the sum of all successful reservations never exceeds seeded stock. 5. If any aggregate requested quantity exceeds availability, the API returns HTTP 409 with the existing `ApiError` shape; the request creates no reservation lines and changes no available quantity. 6. A zero, negative, missing, or non-whole-number quantity is rejected as HTTP 400 with `ApiError`, without changing stock or reservations. 7. An unknown job or part is rejected as HTTP 404 with `ApiError`; an existing job whose status is not `SCHEDULED` is rejected as HTTP 409; each rejected request leaves stock and reservations unchanged. 8. Stock and reservation errors are visible in the UI, and HTTP calls are made through an Angular service rather than a component. 9. Feature 1's booking behavior remains unchanged: overlapping bookings under its 45-minute buffered interval rule are rejected with HTTP 409, exactly 45 minutes between jobs is allowed, and reserving parts neither creates nor alters a job or its booked slot. |
